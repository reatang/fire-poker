# 工具注册与装配机制

工具管理契约位于 `backend/pkg/agent/toolkit`，具体工具位于 `backend/pkg/agent/tools`。管理器不导入具体工具实现；Agent 在组合入口注册实现，再通过接口构造当前会话所需工具。

```text
Agent 组合入口
  |-- tools.RegisterDefaults --> Registrar.Register(Definition)
  |-- MCP / CLI Provider ----> Registrar.RegisterProvider(name, Provider)
  |
  v
toolkit.Manager 接口 <--- toolkit.Registry 实现
  |-- 元数据查询与发现
  |-- 按 Scope 筛选并调用 Factory
  `-- 调用已注册 Provider 构造扩展工具集
  |
  v
SDK Tool / ToolSet --> Agent Runner
```

## 接口职责

| 契约 | 职责 |
| --- | --- |
| `Meta` | 工具名称、描述、分类、确认标记、用途格式化 |
| `Scope` | 本次构造的会话 ID、会话类型和工具选择 |
| `Definition` | 将元数据、适用条件、Factory 和列表展示标记绑定为一个注册项 |
| `Registrar` | 注册本地工具定义和动态工具集 Provider |
| `Manager` | 查询目录并按会话构造 Tool、ToolSet |
| `Dependencies` | 工具实现所需的有类型服务接口，由组合入口延迟注入 |

注册表维护插入顺序，拒绝重名、空名称、缺失 Factory 和无效分类。Factory 返回名称必须与注册名称一致。适用条件不满足的工具不实例化；构造错误携带工具或 Provider 身份向上传递。

## 新增本地工具

1. 在 `tools` 中实现工具及元数据函数。
2. 在 `DefaultDefinitions` 中添加一个定义，提供适用条件和 Factory。需要服务时，在 `Dependencies` 中声明相应接口，并在组合入口注入。
3. 增加覆盖实际行为的测试。管理器不需要添加工具名称分支。

也可以直接使用 `manager.ToolRegistry().Register(toolkit.Definition{...})` 注册应用专用工具。显式传入 `Scope.EnabledTools` 时，所有本地工具（包括未展示的 builtin）都必须按工具 ID 选择，最终仍受可用性条件限制。未传选择的 `nil` 保留旧调用方默认 builtin 的兼容行为；明确的空数组表示不向 LLM 提供任何本地工具。正常会话会先解析已保存的工具选择，空选择必须保留为空数组。

`Listed` 仅控制用户工具列表的展示，不赋予绕过会话选择的权限；执行前权限确认仍由独立回调实现负责。列表展示与运行时目录都来自 `DefaultDefinitions`，不再单独维护第二份能力清单。任务需要的内部工具也须在任务会话选择中显式包含其 ID。

## 全局默认值与会话选择

| 设置 | 持久化位置 | 生效范围 |
| --- | --- | --- |
| 全局默认工具 | `config.json` 的 `default_tool_ids` | 新建会话时复制一份；不修改已有会话 |
| 会话工具选择 | SQLite `sessions.tool_ids`，JSON 数组 | 首条消息前可修改；对话开始后锁定，切换、重开、重试和快捷聊天均沿用 |

全局设置入口为“插件与工具 → 系统工具”：中间列表固定显示系统工具入口，选中后右侧展示工具列表与默认启用设置。会话入口为聊天框的工具菜单。两者独立调用保存接口。首次修改全局设置前，尚无工具配置的旧会话会按旧默认值补齐，避免继承后来的全局变更。空数组必须保留，不能视为尚未配置。分叉会话复制来源会话的工具选择。

“应用”提交当前草稿后重新读取 `config.json` 并校验回读结果；不一致或保存失败时保留草稿并显示错误。配置仍以文件为准，不迁入数据库。各模块统一通过 `configfile` 保存：进程内互斥锁和 `.config.lock` 文件锁覆盖读取最新值、修改和提交的完整过程；仅合并当前模块负责的字段，再通过同目录临时文件替换，避免插件探测等延迟操作用旧配置覆盖工具选择。读取和写入均以当前解析的数据目录为准，便携包搬迁后不沿用配置内残留的旧目录。

工具设置接口返回 `locked` 状态，前端结合本地消息与生成状态立即禁用选择。后端写入以数据库中的消息存在性为条件，并与首轮生成预留互斥；后续发送只能省略工具选择或提交与已保存集合相同的选择，不能借发送或重试修改。归档消息不解除锁定。

## 新增扩展来源

通过 `RegisterProvider` 提供返回 SDK `ToolSet` 的构造函数，无需修改 Agent 的装配流程。MCP 和 CLI 是当前两个已注册来源。扩展按照组 ID 或已发现工具 ID 选择；未选择的扩展不加载。已选择扩展的配置、Manifest 或运行时不可用时，错误传递到 Runner 创建方。

## 生命周期与边界

| 场景 | 机制 |
| --- | --- |
| 不同会话 | Factory 接收不同 Scope，Runner 缓存按会话区分 |
| 新增注册项 | 注册表版本变化，后续请求重新装配 Runner |
| 服务重新注入 | 服务版本变化并清理 Runner 缓存 |
| 查询注册表 | 锁内读取快照；Factory 和 Provider 在注册表锁外执行 |
| 具体工具安全规则 | 仍由既有审批回调与执行实现负责，本次不调整审批策略 |

Factory 应只构造工具实例，不执行有副作用的业务操作。会话身份不能放进进程级共享实例；具体工具通过 Factory 绑定当前 Scope，或在执行时读取可信运行上下文。

## 验证

基础设施测试覆盖注册校验、构造错误、工具身份、筛选顺序、会话作用域、Provider 装配及缓存失效。默认目录测试构造全部 20 个本地工具，校验名称一致性和发现列表。相关管理器构造测试不依赖 SQLite。
